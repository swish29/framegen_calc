How the model works

 
frame time      = 1000 / base FPS
FG overhead(M)  = shared + (M − 1) × per-frame cost, or 0 with FG off
real frame time = frame time + FG overhead(M)
real FPS        = 1000 / real frame time
displayed FPS   = real FPS × M

Why the gain is less than ×M

The GPU computes every generated frame. That work adds to the time the game takes to produce each rendered frame, so the game renders fewer real frames. Displayed FPS is M times this lower real FPS, not M times the base FPS. Each higher multiplier adds more work, so each step gains less.

Shared and per-frame costs

NVIDIA's DLSS 4 research page splits Multi Frame Generation into two parts. One part runs once for each pair of rendered frames, and its output is reused. The other, much smaller part runs once for each generated frame. So the first generated frame isn't slower than the others. Measured times follow this pattern. The DLSSG for SM86 timings for an RTX 3080 Ti at 4K fit 0.80 ms + (M − 1) × 1.10 ms to within 0.01 ms. Other implementations may scale differently, and some use a different network for each multiplier. Your numbers takes a separate value for each multiplier.

Why a fixed cost hurts more at high FPS

Overhead is a fixed time, not a percentage. 1.5 ms is 2.5 % of a 60 ms frame at 16.7 FPS, but 30 % of a 5 ms frame at 200 FPS. A higher base FPS means a shorter frame, so the same overhead takes a larger share of it. The real FPS penalty grows and the displayed FPS gain shrinks.

Why real FPS drops while displayed FPS rises

Displayed FPS counts every frame sent to the display, rendered or generated. Real FPS counts only the frames the game simulates and renders. Frame generation makes each real frame take longer, so any overhead above zero puts real FPS below base FPS, even when displayed FPS goes up.

GPU time and effective overhead

The calculator needs effective overhead, meaning how much longer each real frame takes. This can differ from how long the frame generation passes run on the GPU. If that work overlaps with rendering, the effective cost is lower. If it competes with rendering for GPU compute or memory bandwidth, the effective cost is higher. Measured data marks which kind each source gives. Enter FPS you measured in Your numbers to include these effects.

Displayed FPS is not latency

Generated frames come from rendered frames, so they don't respond to new input. Input latency follows the real frame rate. Interpolation also holds back each rendered frame until the next one is ready, which adds delay. With frame generation on, latency is usually higher than at the same FPS rendered natively, and often higher than with it off.

Limits of the estimate

The real cost depends on the GPU, resolution, frame generation version, driver, and the game's own GPU and CPU load. The model ignores frame pacing, refresh-rate caps and VRR. Without a measurement for your setup, use the results to compare trends, not to predict FPS on a specific GPU.
